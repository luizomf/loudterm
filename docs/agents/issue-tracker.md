# Issue tracker: GitHub

Use GitHub Issues in `luizomf/loudterm` through `gh` for specs, tickets, issues,
and wayfinder maps. Infer the repository from `git remote -v`.

## Operations

- Create: `gh issue create --title "..." --body-file <file>`.
- Read: `gh issue view <number> --comments`; use JSON for body, labels, author,
  dates, and comments when needed.
- Discover: `gh issue list --state open --json number,title,labels,author,comments`.
- Comment: `gh issue comment <number> --body-file <file>`.
- Labels: `gh issue edit <number> --add-label "..." --remove-label "..."`.
- Close: `gh issue close <number> --comment "..."`.

Prefix comments or issue bodies posted during triage with
`> *This was generated by AI during triage.*`.

## Pull requests as a triage surface

**PRs as a request surface: yes.**

Use `gh pr view <number> --comments`, `gh pr diff <number>`, and the corresponding
`gh pr comment`, `gh pr edit`, and `gh pr close` operations. Check the PR's
current state before reviewing, updating, or commenting. Treat merged or closed
PRs as read-only historical records: do not modify or comment on them unless
explicitly requested; put follow-up work in a new issue or PR. Read the entire
diff and verify behavior before recommending a merge; never execute unreviewed
PR scripts or infer safety from an author's description.

Discover external PRs with `gh pr list --state open --json number,title,author,labels,comments`.
Fetch each author's association with
`gh api repos/luizomf/loudterm/pulls/<number> --jq .author_association`.
Include `CONTRIBUTOR`, `FIRST_TIME_CONTRIBUTOR`, and `NONE`; exclude `OWNER`,
`MEMBER`, and `COLLABORATOR` for discovery only. Explicitly named PRs are always
eligible for review.

GitHub issues and PRs share a number space. Resolve bare references with
`gh pr view <number>`, falling back to `gh issue view <number>`.

## Planning and wayfinding

Publishing a spec or ticket means creating a GitHub issue. Fetch tickets through
`gh issue view <number> --comments`.

For wayfinding, use a `wayfinder:map` issue with child issues linked through
GitHub sub-issues. If unavailable, use a task list in the map and `Part of #<map>`
in each child. Use `wayfinder:<type>` labels for research, prototype, grilling,
or task tickets only when that workflow is actually needed.

Record blockers through native issue dependencies using database issue IDs;
when unavailable, use explicit `Blocked by: #<number>` lines. The frontier is the
map's open, unassigned children with no open blockers, in map order. Claim with
`gh issue edit <number> --add-assignee @me`. Resolve by commenting with evidence,
closing, and updating the map's decisions with a link.

Triage eligibility does not authorize autonomous implementation by itself.
Keep work proportionate to this educational project's scope.
